# 内核编译

## 0 - 总体概览

编译内核的关键步骤速查如下，细节见后文对应小节：

1. 获取源码：下载压缩包或克隆 Git 仓库。
2. 解压到主目录下（Git 克隆可跳过）。
3. 配置内核：`make [x|g|menu]config`，推荐 `make menuconfig`。
4. 构建：`make [-j'n'] all`，生成压缩镜像、`vmlinux`、`System.map`、内核模块及所有 DTB。
5. 安装模块：`sudo make modules_install`，默认装到 `/lib/modules/$(uname -r)/`。
6. 配置 GRUB 与 initramfs（x86 特有）：`sudo make install`。
7. （可选）自定义 GRUB 菜单。

## 1 - 获取内核源码

两条官方渠道：从 [kernel.org](https://www.kernel.org/) 下载压缩包，或克隆 Git 仓库。

**方式一：下载压缩包**

```shell
wget https://cdn.kernel.org/pub/linux/kernel/v5.x/linux-5.15.tar.xz
tar xJf linux-5.15.tar.xz
```

`tar` 的 `J` 选项表示 xz 解压。若在意完整性，可下载官网的 GPG 签名与校验和进行比对。

**方式二：克隆 Git 仓库**

只编译、不参与开发时，用浅克隆省磁盘、跳过完整提交历史：

```shell
git clone --depth 1 --branch v5.15 https://github.com/Bartonzany/linux.git linux-5.15
```

- `--depth 1`：只拉目标分支最新一次提交。
- `--branch v5.15`：检出 v5.15 标签。
- 浅克隆不影响编译，只是看不到完整历史。

**版本选择**。kernel.org 的内核分三类：

- `mainline`：主线，含最新特性。
- `stable`：稳定版，由 Greg Kroah-Hartman 维护，生产环境优先。
- `longterm`：长期支持版（如 5.15、6.1），维护周期更长。

本文以 longterm 内核 v5.15 为例。

## 3 - 内核配置

内核的配置与构建依托 kbuild 系统，它通过四个组件串联整个流程：

- `CONFIG_FOO` 符号
- 菜单规范文件 `Kconfig`
- `Makefile`
- 内核整体配置文件 `.config`

| kbuild 组件 | 用途 |
| --- | --- |
| 配置符号 `CONFIG_FOO` | 每个可配置项对应一个宏，取值 `y`/`m`/`n`：<br>- `y`：编进内核镜像<br>- `m`：编译为内核模块<br>- `n`：不编译<br>在 `make menuconfig` 中定位选项后按 `<Help>` 可查到准确名称。 |
| `Kconfig` 文件 | 定义 `CONFIG_FOO` 符号的类型（布尔、三态、数字等）与依赖树；菜单项本身也定义于此。 |
| `Makefile` | kbuild 采用递归式 Makefile，根目录为顶层 Makefile，各子目录各有一个负责编译本目录源码。5.4 内核源码树有 2500 多个 Makefile。 |
| `.config` 文件 | 最终配置以 ASCII 文本保存在源码树根目录，是关键资产，务必妥善保存。 |

### 3.1 默认配置的查找顺序

默认配置按优先级回退查找，列表及顺序（越靠前优先级越高）定义于 `init/Kconfig` 的 `DEFCONFIG_LIST`：

```shell
$ cat init/Kconfig
config DEFCONFIG_LIST
    string
    depends on !UML
    option defconfig_list
    default "/lib/modules/$(shell,uname -r)/.config"
    default "/etc/kernel-config"
    default "/boot/config-$(shell,uname -r)"
    default ARCH_DEFCONFIG
    default "arch/$(ARCH)/defconfig"
config CC_IS_GCC
[...]
```

Kconfig 内核文档对 `defconfig_list` 的解释：

> `defconfig_list`：声明一组默认条目，用于在主 `.config` 尚不存在时查找默认配置。

kbuild 按优先级依次检查 `/lib/modules/$(uname -r)/.config`、`/etc/kernel-config`、`/boot/config-$(uname -r)` 等，找到即用。只要源码树根目录已有 `.config`，上述回退机制全部失效，以该文件为准。

菜单项前方的符号含义：

- `[.]`：布尔选项（开或关）：
  - `[*]`：开，编进内核镜像（`y`）
  - `[ ]`：关，不编译（`n`）
- `<.>`：三态（tristate）选项，三种状态之一：
  - `<*>`：开，编进内核镜像（`y`）
  - `<M>`：模块，编成内核模块（`m`）
  - `< >`：关，不编译（`n`）
- `{.}`：存在依赖，必须以模块（`m`）或编入内核（`y`）的方式编译
- `-*-`：存在依赖，要求必须编入内核（`y`）
- `(...)`：提示符，需输入字母数字（光标停在该项上按回车弹出输入框）
- `<菜单项>  --->`：还有子菜单（按回车进入）

根目录下的 `Kconfig` 负责填充 menuconfig 初始界面，通过 `source` 引入各目录下的其他 `Kconfig` 文件。较重要的 `Kconfig*` 文件与对应菜单：

| 菜单 | 对应的 Kconfig 文件位置 |

| 电源管理 | `kernel/power/Kconfig` |
| 固件驱动 | `drivers/firmware/Kconfig` |
| 虚拟化 | `arch/<arch>/kvm/Kconfig` |
| 通用架构相关选项 | `arch/Kconfig` |
| 启用块层 + I/O 调度器 | `block/Kconfig` |
| 可执行文件格式 | `fs/Kconfig.binfmt` |
| 内存管理选项 | `mm/Kconfig` |

| 设备驱动 | `drivers/Kconfig`、`drivers/*/Kconfig` |
| 文件系统 | `fs/Kconfig`、`fs/*/Kconfig` |

### 3.4 常用配置目标

除交互式配置外，kbuild 还提供若干快捷目标：

| 目标 | 说明 |
| --- | --- |
| `make defconfig` | 使用架构默认配置（如 `arch/x86/configs/x86_64_defconfig`），快速得到可用基础配置 |
| `make olddefconfig` | 基于现有 `.config`，新增选项全部取默认值，内核升级迁移配置的首选 |
| `make oldconfig` | 与 `olddefconfig` 类似，但逐条询问新增选项 |
| `make localmodconfig` | 以 `lsmod` 加载的模块为准精简配置，只保留实际用到的驱动，可缩短编译时间 |
| `make localyesconfig` | 将 `localmodconfig` 中作为模块（`m`）的特性改为编入内核（`y`） |

其中 `olddefconfig` 最常用：拿到旧版 `.config` 后执行它，几乎零交互即可迁移到新内核。

## 4 - 内核编译

### 4.1 编译命令

配置完成后即可构建。构建前可先用 `nproc` 确认可用逻辑核数，用并行编译提速：

```shell
nproc              # 查看可用逻辑核数
make -j$(nproc)    # 并行编译
```

`-jN` 让 make 同时运行 N 个作业，通常取 `-j$(nproc)` 以充分利用多核。构建完成后生成的关键产物：

| 产物 | 说明 |
| --- | --- |
| `vmlinux` | 未压缩的内核 ELF 镜像，位于源码树根目录，`objdump`、调试器常用对象 |
| `arch/<arch>/boot/bzImage` | x86 的压缩可引导镜像，引导加载程序读取的就是它 |
| `arch/<arch>/boot/Image` | 未压缩的可引导镜像；ARM/ARM64 等架构用 `Image` 而非 `bzImage` |
| `System.map` | 内核符号表，记录符号地址与名称对应关系，供调试与 oops 回溯使用 |
| `*.ko` | 编译出的内核模块目标文件，分散在各目录 |
| `*.dtb` | 设备树二进制文件（ARM 等架构） |

> `vmlinux` 是未压缩镜像，不能直接引导；`bzImage` 含自解压头，才可被 GRUB 直接加载。

### 4.2 常用编译指令

**安装内核模块：**

```shell
sudo make modules_install
```

默认安装到 `/lib/modules/$(uname -r)/`。若编译对象并非当前运行内核（如交叉编译），用 `INSTALL_MOD_PATH` 指定目标根目录。

**清理目标**。kbuild 提供三种由浅入深的清理级别：

| 目标 | 作用 |
| --- | --- |
| `make clean` | 删除绝大多数生成的目标文件，保留 `.config`，便于增量编译 |
| `make mrproper` | 在 `clean` 基础上再删除 `.config` 及备份，回到"干净"状态 |
| `make distclean` | 在 `mrproper` 基础上进一步删除编辑器备份等，最接近发布状态 |

`mrproper`/`distclean` 会清掉 `.config`，重新构建前务必备份配置。

**外部目录构建（out-of-tree build）**。默认在源码树内就地编译，会让源码树遍布目标文件。用 `O=` 指定输出目录即可保持源码树只读：

```shell
mkdir -p ../build
make O=../build defconfig
make O=../build -j$(nproc)
```

一份源码由此可同时支撑多个配置、面向多个架构的构建，互不干扰。

**交叉编译**。目标架构与主机不同时，用 `ARCH` 指定架构、`CROSS_COMPILE` 指定工具链前缀：

```shell
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- defconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)
```

`CROSS_COMPILE` 末尾的连字符不可省略，它会被拼接到 `gcc`、`ld` 等工具名前。

### 4.3 编译执行

执行 `make -j32`：

```shell
  LD      vmlinux.o
  MODPOST vmlinux.symvers
  MODINFO modules.builtin.modinfo
  GEN     modules.builtin
  LD      .tmp_vmlinux.kallsyms1
ld: warning: .tmp_vmlinux.kallsyms1 has a LOAD segment with RWX permissions
  KSYMS   .tmp_vmlinux.kallsyms1.S
  AS      .tmp_vmlinux.kallsyms1.S
  LD      .tmp_vmlinux.kallsyms2
ld: warning: .tmp_vmlinux.kallsyms2 has a LOAD segment with RWX permissions
  KSYMS   .tmp_vmlinux.kallsyms2.S
  AS      .tmp_vmlinux.kallsyms2.S
  LD      vmlinux
ld: warning: vmlinux has a LOAD segment with RWX permissions
  SORTTAB vmlinux
```

内核镜像与 `vmlinux` 是同一内核的两种形态：

- kbuild 先把各源文件编译成目标文件（`.o`），再由链接器按符号依赖拼成一个未压缩的 ELF 映像，即 `vmlinux`。
- `vmlinux` 再经 `objcopy` 剥除调试节、对齐，得到可供引导加载程序加载的 `arch/arm64/boot/Image`。
- 输出末尾的 `LD vmlinux` 即链接完成的标志；完整流程还会继续生成 `System.map` 符号表。

本机为 ARM64，最终镜像是未压缩的 `Image`；x86 上则是带自解压头的 `bzImage`。

## 5 - 安装内核模块

用 `INSTALL_MOD_PATH` 指定一个"暂存根目录"（staging root），让模块装到该目录而非主机根目录 `/`：

## 6 - initramfs 与 bootloader

生成 initramfs（initial ram filesystem，初始内存文件系统）镜像并更新引导加载程序，在 x86[_64] 的 Ubuntu 上一步完成：

```shell
sudo make install
```

`sudo make install` 实际完成三件事：

1. 调用 `mkinitramfs`（Debian/Ubuntu）或 `dracut`（RHEL/Fedora）生成 initramfs 镜像并写入 `/boot`。
2. 把内核镜像 `vmlinuz-<版本>`、`System.map` 与 `.config` 一并拷贝到 `/boot`。
3. 运行 `update-grub`（Ubuntu）/`grub2-mkconfig`（RHEL 系）更新 GRUB 配置，使新内核成为默认启动项。

### 6.1 理解 initramfs 框架

initramfs（前身 initrd）是内核早期启动与用户态之间的一层中间层：在挂载真正根文件系统之前，先运行用户态程序或脚本——这件事内核在启动阶段本身做不了。

**为什么需要它**：

- 启动初期无法预知关键信息：引导盘依赖的控制器类型（SCSI、RAID 等）、根文件系统格式（ext2/3/4、btrfs、reiserfs、f2fs 等）。
- 这些支撑能力常以模块（`=m`）存在，内核挂载根文件系统前还加载不了。
- 由 `CONFIG_BLK_DEV_INITRD` 控制，默认开启（`=y`）。
- 术语上 initrd 已算旧称，现在更通行的说法是 initramfs。

**鸡生蛋问题**。发行版无法预知用户把磁盘格式化成什么文件系统，只能把各种模块都打包提供。用户启动时，内核需要 `reiserfs.ko` 才能挂载根文件系统，但这个模块文件本身就在 reiserfs 根文件系统里（`/lib/modules/<版本>/kernel/fs/reiserfs/`）。挂载根文件系统要先加载模块，加载模块又要先能读到根文件系统——循环就此形成。

**initramfs 如何破解**：

- initramfs 镜像本质是一个通常经 gzip 压缩的 cpio 归档（cpio 是与 tar 类似的扁平归档格式）。
- Ubuntu 上 `update-initramfs` 调用 `mkinitramfs`，把所需模块与 `/etc`、`/lib` 等支撑目录打成最小根文件系统，再压缩成 `/boot/initrd.img-<版本>`。
- 启动时引导加载程序把镜像载入 RAM，内核解压后用其中脚本加载挂载所需的模块，再挂载真正的根文件系统。

**常见应用**：

- 设置控制台字体；
- 定制键盘布局；
- 打印自定义欢迎信息；
- 接收加密磁盘解锁口令；
- 按需加载内核模块；
- 启动失败时进入 rescue 救援 shell。

### 6.2 什么时候才需要 initramfs

只有根文件系统在真实磁盘上、且 SATA/NVMe/LVM/LUKS/RAID 等驱动被编译成模块（`=m`）时，才需要 initramfs 提前加载这些模块。**本实验不属于此类**：QEMU 直接加载内核，根文件系统是 9p，必需驱动都已内建（`=y`），内核一启动就能挂载 rootfs，没有 initramfs 的用武之地。启动链路：

```text
qemu-system-aarch64 -kernel out/arm64/arch/arm64/boot/Image   # 直接加载内核
  → 内核挂载 9p rootfs（rootfstype=9p）                       # 9p/virtio 驱动均内建 =y
  → init=/bin/sh
```

其中 9p 与 virtio 相关驱动均已内建：`CONFIG_9P_FS=y`、`CONFIG_NET_9P=y`、`CONFIG_NET_9P_VIRTIO=y`、`CONFIG_VIRTIO=y`、`CONFIG_VIRTIO_PCI=y`、`CONFIG_VIRTIO_NET=y`、`CONFIG_VIRTIO_BLK=y`。

### 6.3 为什么不会破坏服务器引导

当前流程完全不触碰服务器的引导：

| 危险操作 | 脚本是否使用 |
| --- | --- |
| `make install`（往 `/boot` 装内核） | 否 |
| `update-grub` / `grub-install` | 否 |
| `mkinitramfs` / `dracut` / `update-initramfs` | 否 |

隔离机制：

1. **产物隔离**：`build.sh` 全程使用 `O=out/arm64`，内核镜像与 `vmlinux` 都落在 `out/arm64/`，从不写 `/boot`。
2. **模块隔离**：`modules_install` 带 `INSTALL_MOD_PATH`，装到 `out/arm64/modules` 或 rootfs 目录，不写宿主机 `/lib/modules`。
3. **版本独立**：服务器运行内核是 `5.10.0-...-hce2.aarch64`，编译的是 `5.15.0-dirty`，互不关联。
4. **QEMU 纯用户态**：QEMU 只读 `out/arm64/arch/arm64/boot/Image` 与 rootfs 目录，与服务器运行中的内核、grub、`/boot` 无关。

因此，只要不主动在服务器本机替换内核，`make install`、`update-grub`、`mkinitramfs` 一个都不会触发，当前流程怎么跑都安全。

## 7 - 定制 GRUB 引导菜单

定制 GRUB 引导菜单（可选，x86[_64] 物理机/虚拟机场景）。编辑前先备份：

```shell
sudo cp /etc/default/grub /etc/default/grub.orig
```

`/etc/default/grub` 是 GRUB 的用户配置文件，用任意编辑器打开：

```shell
sudo vi /etc/default/grub
```

为让 GRUB 每次启动都显示菜单，插入下面这行：

```text
GRUB_HIDDEN_TIMEOUT_QUIET=false
```

若发行版用的是 `GRUB_TIMEOUT_STYLE=hidden`，改成 `GRUB_TIMEOUT_STYLE=menu` 也能达到同样效果。

`GRUB_TIMEOUT` 设置菜单显示时长（默认约 10 秒）：

| 取值 | 含义 |
| --- | --- |
| `0` | 不显示菜单，立即启动 |
| `-1` | 无限期等待用户选择 |
| `N`（如 `3`） | 显示菜单 N 秒，超时后启动默认项 |

例如设为 3 秒：

```text
GRUB_TIMEOUT=3
```

若配置里存在 `GRUB_HIDDEN_TIMEOUT`，注释掉即可：

```text
#GRUB_HIDDEN_TIMEOUT=1
```

改完后以 root 身份运行 `update-grub` 使改动生效：

```shell
sudo update-grub
```

编辑后的 `/etc/default/grub` 大致如下：

```text
$ cat /etc/default/grub
[...]
#GRUB_DEFAULT=0
GRUB_DEFAULT="Advanced options for Ubuntu>Ubuntu, with Linux 5.0.0-36-generic"
#GRUB_TIMEOUT_STYLE=hidden
GRUB_HIDDEN_TIMEOUT_QUIET=false
GRUB_TIMEOUT=3
GRUB_DISTRIBUTOR=`lsb_release -i -s 2> /dev/null || echo Debian`
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"
GRUB_CMDLINE_LINUX=""
[...]
```

几点补充：

- 可做美化微调，如用 `BACKGROUND_IMAGE="<图片文件>"` 更换背景图或颜色。
- Fedora 的 GRUB 配置略有不同，要让每次启动都显示菜单，可执行 `sudo grub2-editenv - unset menu_auto_hide`（详见 Fedora wiki 的 Changes/HiddenGrubMenu）。
- GRUB2 在各发行版上的实现有差异，同一套调优方式往往不兼容。

改好后重启（`sudo reboot`），GRUB 菜单出现时按任意键打断倒计时，即可选择并引导新编译的内核。

> **注**：本节属 x86[_64] 物理机/虚拟机场景。本实验（ARM64 + QEMU）不使用 GRUB，内核由 QEMU 直接加载（见 `shell_scripts/run_qemu.sh`），此节仅作参考。

## 10 - 内核调试（gdb / kprobe / ftrace / eBPF）

本章记录的调试通常是三类工具：gdb 静态断点调试、kprobe/ftrace 动态追踪、eBPF（bpftrace）。三者都依赖内核侧相应配置，而默认 `defconfig` 并没有把它们全部打开。

### 10.1 启用调试配置

先查看当前配置——`CONFIG_DEBUG_INFO` 虽已开启，但 `KPROBES`、`FTRACE`、`BPF_SYSCALL` 等默认都是关闭的：

```shell
$ grep -E 'CONFIG_(KPROBES|FTRACE|BPF_SYSCALL|DEBUG_INFO)=' out/arm64/.config
CONFIG_DEBUG_INFO=y
```

用 `scripts/config` 批量启用后再同步配置并重编译：

```shell
scripts/config --file out/arm64/.config \
  -e KPROBES -e KPROBE_EVENTS -e UPROBES -e UPROBE_EVENTS \
  -e FTRACE -e FUNCTION_TRACER -e FUNCTION_GRAPH_TRACER -e DYNAMIC_FTRACE \
  -e BPF_SYSCALL -e BPF_EVENTS -e BPF_KPROBE_OVERRIDE \
  -e GDB_SCRIPTS
make O=out/arm64 ARCH=arm64 olddefconfig
./shell_scripts/build.sh arm64          # 重编译 2m22s，Image 32M -> 39M
```

重编译后启动日志出现 `ftrace: allocating 58030 entries in 227 pages`，说明 ftrace 已启用。各配置项用途：

| 配置 | 作用 |
| --- | --- |
| `KPROBES` / `KPROBE_EVENTS` | 内核动态探针，可把探针挂到任意内核函数入口 |
| `UPROBES` / `UPROBE_EVENTS` | 用户态动态探针 |
| `FTRACE` / `FUNCTION_TRACER` | 函数级追踪框架，tracefs 的基础 |
| `BPF_SYSCALL` / `BPF_EVENTS` | eBPF 系统调用与事件，bpftrace 的前提 |
| `GDB_SCRIPTS` | 生成 `vmlinux-gdb.py`，向 gdb 注册 `lx-*` 命令 |

重编译后需把模块重新装回 rootfs，否则新模块与内核版本不匹配：

```shell
./shell_scripts/build.sh arm64 modules_install /home/developer/kernel-rootfs-arm64
```

### 10.2 gdb 调试

`run_qemu.sh --gdb` 会以 `-s -S` 启动 QEMU：`-s` 监听 gdb 端口 1234，`-S` 启动后立即暂停，等待 gdb 连接。用 `gdb_kernel.sh` 包装 gdb：

```shell
./shell_scripts/run_qemu.sh --gdb        # 终端 1：QEMU 暂停，等 gdb
./shell_scripts/gdb_kernel.sh out/arm64/vmlinux   # 终端 2：加载内核符号
```

**为什么必须用 `gdb_kernel.sh`**。它把 `LD_LIBRARY_PATH` 指到系统完整 libpython。直接跑 gdb 时，`source vmlinux-gdb.py` 会因精简版 Python 缺 `zlib` 而失败：

```text
Python Exception <class 'ModuleNotFoundError'>: No module named 'zlib'
Undefined command: "lx-version".
```

包装后即可正常加载 `lx-*` 命令。连接并设断点的实际输出：

```text
(gdb) target remote :1234
Remote debugging using :1234
0x0000000040000000 in ?? ()                ← QEMU -S 暂停在 reset 向量
(gdb) hbreak start_kernel
Hardware assisted breakpoint 1 at 0xffff800011a00cdc: file init/main.c, line 936
```

几点说明：

- **`hbreak` 是硬件断点**，arm64 只有 6 个硬件断点寄存器（启动日志 `found 6 breakpoint and 4 watchpoint registers`），故用 `hbreak`；普通 `break` 在 MMU 未启用的早期阶段无法写内存。
- **KASLR 会让断点错位**：`start_kernel` 的符号地址是链接地址，而启动日志有 `KASLR enabled`，实际运行地址被随机偏移，直接 `hbreak start_kernel` 后 `continue` 往往不命中。要断在内核最早入口，需在 `-append` 加 `nokaslr`。
- **加载 `lx-*` 命令**：`source out/arm64/vmlinux-gdb.py` 后可用 `lx-version`、`lx-dmesg`、`lx-ps`、`lx-lsmod`、`lx-cpus`、`lx-symbols` 等在 gdb 内查看内核状态：

```text
(gdb) lx-version
Linux version 5.15.0-dirty (developer@...) (gcc ... 13.3.0, GNU ld ... 2.42) #7 SMP PREEMPT Tue Nov 10 17:38:27 CST 2026
```

- gdb 首次会拒绝对 `scripts/gdb/vmlinux-gdb.py` 的自动加载（`auto-load safe-path`），可加 `set auto-load safe-path /` 放行。

### 10.3 kprobe 与 ftrace

在 guest 里挂载 debugfs 后，tracefs 即可用（`--debug` 模式需手动挂载）：

```shell
mount -t proc proc /proc
mount -t sysfs sysfs /sys
mount -t debugfs debugfs /sys/kernel/debug
```

```shell
# ls /sys/kernel/debug/tracing/
instances        kprobe_events      set_ftrace_pid      trace_pipe
available_events kprobe_profile     current_tracer      trace_marker
available_tracers uprobe_events     set_ftrace_filter   tracing_on
...
```

动态注册一个 kprobe（挂在 `do_sys_open` 入口）并回读：

```shell
# echo 'p:myprobe do_sys_open' > /sys/kernel/debug/tracing/kprobe_events
# cat /sys/kernel/debug/tracing/kprobe_events
p:kprobes/myprobe do_sys_open
```

Kprobe 由此注册成功。配合 `trace_pipe` 即可实时观察该函数的调用（`echo 1 > events/kprobes/myprobe/enable` 后再 `cat trace_pipe`）。

### 10.4 tracepoint

除函数级 kprobe 外，内核还提供静态 tracepoint。`events/` 目录下列出的即各子系统已埋点的事件：

```shell
# ls /sys/kernel/debug/tracing/events/ | head
9p  alarmtimer  block  bpf_trace  cgroup  ext4  ftrace  gpio ...
```

注意其中没有 `syscalls` 子系统——需要额外开启 `CONFIG_FTRACE_SYSCALLS` 才会有 `tracepoint:syscalls:sys_enter_*` 这类事件。

### 10.5 eBPF / bpftrace

rootfs 里已装好 `bpftrace`，内核侧 kprobe/bpf 也已就绪。但实测运行时报错——eBPF 程序编译时 clang 找不到内核头文件：

```text
# bpftrace -e 'kprobe:do_sys_open { @[comm] = count(); }' -c '/bin/ls /'
/bpftrace/include/clang_workarounds.h:14:10: fatal error: 'linux/types.h' file not found
```

原因是 rootfs 缺少 `linux-libc-dev` 头文件。两种修复方向：

- chroot 进 rootfs 安装 `linux-libc-dev`（legacy 模式，无需 BTF）；
- 或在内核开启 `CONFIG_DEBUG_INFO_BTF` 走 BTF 模式（但 `config_debug.sh` 明确关闭了 BTF，因该工具链下有编译报错）。

这也解释了 `scripts/config_debug.sh` 的作用：它本质就是把本节这些调试配置（debuginfo、kprobe、ftrace、bpf、gdb_scripts 等）一次性写入 `.config`，再 `olddefconfig` 生成一个"调试内核"。其内容与本节的 `scripts/config -e ...` 等价，只是它面向 x86_64 且路径写死，移植到 arm64 时需改 `ARCH` 与输出目录。
